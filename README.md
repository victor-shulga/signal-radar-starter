# Signal radar starter

Шаблон сигнал-радара до курсу «AI-native аутріч для агенцій» (тиждень 4, урок 08) від [Victor Shulga](https://victorshulga.com).

Радар раз на день чи тиждень забирає вакансії, новини або тендери, веде стан кожного об'єкта і віддає лише те, що змінилось: нову подію, вакансію, що висить понад N днів, або передрук після зникнення. На виході CSV з колонками блоку «Сигнал» шаблону проспект-листа.

## Швидкий старт

```bash
git clone https://github.com/victor-shulga/signal-radar-starter && cd signal-radar-starter
python3 test_radar.py                # перевірка, мережа не потрібна
cp config.example.json config.json   # заповніть під свою картку радара
export APIFY_TOKEN=...               # токен з apify.com → Settings → Integrations
python3 radar.py config.json
```

Що де лежить:

| Файл | Навіщо |
|---|---|
| `radar-card.md` | картка радара: заповнити до конфігу |
| `config.example.json` | приклад конфігу радара вакансій |
| `radar.py` | забирає дані, веде стан, пише сигнали |
| `prompt.md` | готовий запит для Claude Code, щоб зібрати радар під себе |
| `state/<name>_state.csv` | стан на кожен об'єкт: `first_seen`, `last_seen`, `runs`, `gone_at`, `reappeared` |
| `state/<name>_signals.csv` | нові сигнали, кожен лише один раз |
| `state/runs.csv` | рядок на кожен прогін, навіть з нулем |

Правила конфігу: `min_age_days: 0` = кожна нова подія стає сигналом (раунди, призначення). `min_age_days: 60` = сигнал, коли об'єкт висить 60+ днів (старі вакансії). `source.type: "file"` + `path` читає JSON-вивантаження, якщо джерело не Apify.

# Інструкція: як створити сигнал-радар під вашу агенцію

Радар — це невелика програма, яка за розкладом ходить по джерелах і повідомляє, що змінилось з минулого разу. Нова вакансія, раунд, зміна CTO. На виході в проспект-листі з'являється рядок «у цієї компанії сталася подія, ось дата і посилання». Без радара сигнали шукають руками раз на місяць, і половина з них устигає застаріти.

Цього тижня радари запускаєте лише під сигнали трьох гіпотез з уроку 07.

**Що знадобиться:**
- 3–5 сигналів з вашого списку тижня 3, на які стоять три гіпотези
- Claude Code (скіли тижня 4 встановлені однією командою зі слайда «Скіли тижня 4»)
- акаунт Apify (оплата за результат, на старті вистачить $5–10) і, за потреби, Firecrawl для сайтів
- Google-таблиця для стану радара

| Крок | Що робите | Скільки часу |
|---|---|---|
| 1 | Вибираєте позиції каталогу: одна позиція = один радар | 15 хв |
| 2 | Заповнюєте картку радара | 20 хв на радар |
| 3 | Вибираєте джерело, спершу найдешевше | 15 хв |
| 4 | Готуєте таблицю стану | 10 хв |
| 5 | Збираєте радар у Claude Code і робите перший прогін | 40 хв |
| 6 | Перевіряєте знахідки руками | 20 хв |
| 7 | Ставите на розклад | 10 хв |
| 8 | Переносите сигнали в проспект-лист | 15 хв |

## Крок 1. Позиції каталогу

Відкрийте свій список сигналів з тижня 3 і матрицю гіпотез. Випишіть лише ті позиції, на яких стоять три гіпотези в роботі. Зазвичай це 3–5 позицій.

Правило: **одна позиція = один радар**. Якщо два радари ловлять ту саму подію різними словами, покриття від цього не росте, зате у звіті одна подія рахується двічі.

Позиція, яка дає менше 40 компаній на місяць, окремого радара не варта. Об'єднайте її зі спорідненими в один (наприклад, «новий CTO» і «новий VP Engineering»).

## Крок 2. Картка радара

На кожен радар заповніть шість рядків. Без них радар приноситиме схожі події замість вашого сигналу.

| Поле | Приклад для агенції розробки |
|---|---|
| Що ловимо | вакансія backend-розробника висить понад 60 днів |
| Джерело | кар'єрні сторінки компаній і LinkedIn Jobs |
| Запит | назви ролей з вашого оферу: Senior Backend, Python Developer, Tech Lead |
| Стоп-фільтр | кадрові агенції, чужий стек, ваші конкуренти, чинні клієнти |
| Вікно свіжості | 90 днів від дати вакансії, найкраще 60–75 |
| Розклад | раз на тиждень, понеділок |

Запит пишіть з двох частин: ролі (хто потрібен) і слова в описі, що доводять проблему («legacy», «migration», «scale»). Лише роль дасть забагато шуму.

## Крок 3. Джерело

Починайте з найдешевшого шару і переходьте до платного, лише коли безкоштовного не вистачає:

1. Відкриті дані й реєстри: асоціації, тендери, дозволи. Безкоштовно.
2. Стрічки новин і RSS: раунди, призначення. Безкоштовно.
3. Сторінки сайтів: кар'єра, кейси, ціни. Майже безкоштовно через Firecrawl.
4. Агрегатори вакансій через Apify: близько $0,012 за вакансію.
5. Платні бази даних, коли перші чотири не дають обсягу.

У малих фірм (1–50 людей) системи найму зазвичай немає. Тоді беріть LinkedIn Jobs і Indeed замість кар'єрних сторінок.

## Крок 4. Таблиця стану

Головна помилка: зберігати знімок сторінки. По знімку не порахувати, скільки висить вакансія, коли вона зникла і чи її передрукували. Тому ведемо **стан на кожен об'єкт** (вакансію, новину, тендер).

`radar.py` створює цей файл сам (`state/<name>_state.csv`), за потреби імпортуйте його в Google-таблицю. Колонки:

`object_id` · `domain` · `first_seen` · `last_seen` · `runs` · `gone_at` · `reappeared` · `signal_type` · `signal_date` · `signal_evidence_url` · `quote`

- `object_id` — посилання на саму вакансію або новину, щоб не плутати дві однакові
- `first_seen` і `last_seen` дають вік: «висить понад 60 днів» рахується саме з них
- `gone_at` і `reappeared` ловлять сильний сигнал: вакансію зняли, а через тиждень передрукували, отже людину так і не знайшли

Окремий аркуш `runs`: дата прогону, скільки знайдено, скільки нових. Рядок пишеться навіть тоді, коли знайдено нуль. Так ви відрізните «подій не було» від «радар не запускався».

## Крок 5. Збірка в Claude Code

Склонуйте це репо, відкрийте Claude Code у його теці і дайте йому картку радара з кроку 2 (готовий запит у `prompt.md`). `radar.py` уже веде стан і пише різницю, Claude лише підбирає джерело і поля конфігу. Скіл `agency-signal-sourcer` збирає радар, `signal-research` допомагає вибрати джерело. Приклад запиту:

> Збери радар за цією карткою: [вставте картку]. Джерело — Apify, актор для LinkedIn Jobs. Стан веди в Google-таблиці [посилання], колонки як у шаблоні. Кожен прогін: забери нові дані, порівняй зі станом, онови first_seen, last_seen, runs і gone_at, допиши рядок в аркуш runs. У проспект-лист віддавай лише різницю з минулого прогону. Спершу зроби сухий прогін на 20 записах і покажи результат.

Перший прогін завжди робіть на маленькому обсязі. Подивіться, що повернулось, і лише потім запускайте на всьому ринку.

## Крок 6. Перевірка руками

Перші два прогони перегляньте очима. Сигнал іде в проспект-лист лише тоді, коли виконано чотири умови:
- **дата взята з джерела**: дата прогону не годиться
- **посилання відкривається** і веде саме на подію
- **домен компанії** збігається з тим, що у вас у списку
- **цитата** з тексту доводить проблему; згадки ролі мало

За моїми замірами, приблизно одна знахідка з семи виявляється шумом: кадрова агенція, чужий стек, вакансія в іншій країні. Кожну таку причину допишіть у стоп-фільтр картки, щоб наступний прогін її не приносив.

## Крок 7. Розклад

| Тип сигналу | Як часто |
|---|---|
| новини, раунди, призначення | щодня |
| вакансії, тендери | раз на тиждень |
| сайти й портфоліо, реєстри | раз на місяць |
| зміна роботи ОПР | раз на квартал |

Найпростіше поставити регулярне завдання в Claude Code (`/schedule`). Підійде будь-який планувальник, у якому видно, що завдання відпрацювало. Раз на тиждень дивіться аркуш `runs`: радар, який два тижні поспіль приносить нуль, або зламаний, або поставлений на мертве джерело.

## Крок 8. Сигнали в проспект-лист

У шаблоні проспект-листа є блок «Сигнал». Радар заповнює в ньому:

`signal_type` · `signal_date` · `signal_age_days` · `signal_evidence_url` · `signal_summary` · `signal_route`

`signal_route` розкладає акаунти по чергах: A — свіжа сильна подія, пишемо першими; B — слабша або старіша; D — сигналу немає, пишемо з дата-поінту. Компанію без сигналу не викидаємо, вона чекає в черзі D.

## Готово, коли

- на кожну з трьох гіпотез працює хоча б один радар
- кожен радар має заповнену картку і пройшов два прогони
- в аркуші `runs` є рядки за обидва прогони, навіть з нулем
- сигнали в проспект-листі мають дату з джерела, посилання і цитату

## Типові помилки

- **Радар на весь каталог одразу.** Береться п'ятнадцять позицій, жодна не доведена до розуму. Починайте з тих 3–5, на які реально ставите.
- **Знімок замість стану.** Без `first_seen` не дізнаєтесь, що вакансія висить 65 днів, і найсильніший сигнал пропаде.
- **Дата прогону замість дати події.** Сигнал виглядає свіжим, а подія сталася чотири місяці тому.
- **Сигнал як фільтр.** Сигнал лише ранжує акаунти. Компанія без події лишається в базі й чекає в черзі D.
